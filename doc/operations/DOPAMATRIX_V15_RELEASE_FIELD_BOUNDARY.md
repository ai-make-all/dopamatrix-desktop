# DopaMatrix V1.5
# Release / Philippine Field Boundary

## 1. Purpose

This document separates development-owned release production from Philippine field-owned Seed execution. It prevents development runtime state from being mistaken for Philippine P0 evidence and defines the clean handoff required before the first real Seed tenant is operated.

The application release and a tenant's Seed state are independent authorities. A development build, empty development tenant database, local Delivery path, or development backup is never Philippine operational evidence.

## 2. Release vs Seed Boundary

The release boundary ends at a verified, clean installer and its non-secret handoff package. The Seed boundary begins only after that installer is installed on the Philippine field machine.

```text
Development release
  -> signed-off installer + hashes + manifest + safe documentation
  -> Philippine installation and release verification
  -> PH-P0-A INSTALL_AND_SAFE_OFF
  -> REAL_ASSET_INGESTION
  -> PH-P0-B ASSET_READY_BACKUP_AND_VERIFY
  -> P1 EXPLICIT_ENFORCE
  -> P2 READY
  -> P3-W CONTROLLED CANARY
```

Development-machine provisioning acceptance proves only that the schema/identity mechanism works. It does not create or pre-authorize the field tenant.

## 3. Development Responsibilities

Development owns:

- freezing application source at an immutable release tag;
- aligning application and product-facing versions;
- building the PyInstaller backend sidecar and Tauri frontend/installer from an isolated tag-based release staging area;
- proving that ignored development files cannot enter the package;
- producing a clean installer, SHA-256 checksum, and release manifest;
- providing a safe field environment template containing placeholders only;
- providing an explicit packaged tenant-provisioning mechanism and field backup/verify mechanism;
- documenting first-run data roots, installer scope, and required filesystem permissions;
- supplying the Seed Execution Pack, Canary Runbook, tenant identity sheet, backup runbook, and this boundary document;
- preserving release-build evidence without customer content or secrets.

Development does not pre-populate field tenant databases, Delivery output, real creative assets, real secrets, or production Seed evidence.

## 4. Philippine Field Responsibilities

Philippine Operations owns:

- installing the verified release on the designated field machine;
- checking installer and manifest SHA-256 values before first launch;
- verifying application version and release identity;
- provisioning the exact approved `ph-elv-0001` tenant through the approved packaged operator mechanism;
- selecting and verifying field Delivery and Backup roots;
- generating the rollout Assignment Secret locally through a secure operator channel;
- applying the complete SAFE-OFF environment configuration;
- importing and validating real elevator assets;
- creating and independently verifying the real pre-P1 backup;
- executing P1, P2, and P3-W under the frozen policy and staffed change control.

Field Operations must not reuse development tenant databases, development `.env`, development Delivery output, or development backups.

## 5. Clean Release Contract

The installer and handoff package must exclude:

- every development, test, acceptance, or provisioning tenant SQLite database;
- `*.db-wal` and `*.db-shm` files;
- an existing development `dopamatrix.db`;
- any real `.env`, Assignment Secret, API credential, or HMAC material;
- `output/` media, Delivery copies, exports, temporary renders, and backup bundles;
- raw customer creative assets;
- local logs, test fixtures, tests, build caches, debug-only evidence, and developer absolute paths.

Legitimate application components are the Tauri application, frontend bundle, backend sidecar, required runtime libraries, FFmpeg, FFprobe, icons, and other explicitly reviewed non-secret resources. Final inclusion is verified from the built artifact, not inferred from `.gitignore`.

## 6. Secret Boundary

Real secrets are generated or loaded only on the Philippine field machine. In particular:

- `RESERVATION_ROLLOUT_ASSIGNMENT_SECRET` is never generated by Development for production;
- no real secret appears in Git, Markdown, installer resources, release manifest, checksum file, or screenshots;
- the field environment template contains key names and safe placeholders only;
- runtime configuration must persist across controlled restarts through an approved field mechanism;
- an environment file must not be silently bundled from a developer worktree.

The release manifest contains no secret and no customer data.

## 7. Tenant Provisioning Boundary

The clean installer contains no production tenant database. Field provisioning creates only the approved Canonical Tenant ID after release verification:

```text
ph-elv-0001 -> data/dopamatrix_ph-elv-0001.db
```

The operator alias `elv0001` is never a database selector. Provisioning must be explicit, collision-checked, schema-verifying, and available in the packaged handoff without a source checkout or Python virtual environment.

Ordinary Login, diagnostics, or an arbitrary `X-Local-User` value must not be treated as the provisioning procedure. A typo must fail closed rather than lazily allocate a new tenant. This is narrow V1.5 field safety and does not implement the future AUTH-001 membership architecture.

## 8. PH-P0-A

`PH-P0-A INSTALL_AND_SAFE_OFF` consists of:

1. install the verified package;
2. verify release hashes, manifest, tag/commit, and application version;
3. provision exactly `ph-elv-0001` through the approved packaged mechanism;
4. configure and verify the field Delivery Root;
5. configure and verify the field Backup Root;
6. generate and load the Assignment Secret locally;
7. apply the complete Seed environment;
8. set lease TTL/heartbeat to `180/45`;
9. set the tenant allowlist to exactly `ph-elv-0001`;
10. keep Exact bps `0`, Balanced bps `0`, and kill switch `true`;
11. configure diagnostics/Readiness/Rollout without activating Canary;
12. prove ordinary omitted traffic remains `DEFAULT_OFF`.

PH-P0-A creates no Canary exposure and is not complete until the configuration survives the required controlled restart and re-query.

## 9. Real Asset Ingestion Boundary

Real elevator assets are imported only after PH-P0-A on the field machine. Development does not ship them in the installer or handoff package.

Asset ingestion must preserve tenant isolation and internal authoritative storage. Delivery remains an operator-facing copy and is not TaskHistory, backup, Fingerprint, Reservation, or future L3 authority.

## 10. PH-P0-B

`PH-P0-B ASSET_READY_BACKUP_AND_VERIFY` requires:

- authoritative real asset references are complete and usable;
- the tenant remains SAFE-OFF with Exact `0`, Balanced `0`, and kill switch `true`;
- a real tenant backup is created on the field machine using the packaged operator mechanism;
- the backup is independently verified as `VALID`;
- Delivery and Backup roots remain valid and isolated;
- the complete Readiness configuration is present;
- no unresolved authority, persistence, task-lifecycle, database, lease, cleanup, or asset-readiness error remains.

Only PH-P0-B PASS permits P1. A development backup or empty development tenant database cannot satisfy PH-P0-B.

## 11. P1 / P2 / P3-W Boundary

- **P1:** Central Tech Operator submits normal diverse `EXPLICIT_ENFORCE` Balanced tasks, serial through planning, until frozen evidence minima are met. No manufactured contention.
- **P2:** Readiness is exactly `READY_FOR_CONTROLLED_CANARY`; backup/Delivery remain valid; breaker is clear; kill switch remains true.
- **P3-W:** Balanced bps is prepared at `3000` while killed, then the kill switch is disabled last at the beginning of a sufficiently staffed block. Ordinary omitted-mode traffic supplies Canary evidence.

The release process does not perform or pre-claim any of these tenant states.

## 12. Release Manifest Contract

The future manifest minimally records:

- Product: `DopaMatrix`;
- application version;
- immutable application tag and commit;
- UTC build timestamp;
- Windows architecture/target triple;
- installer type and filename;
- installer SHA-256;
- backend sidecar SHA-256 when independently useful;
- clean-staging and exclusion verification result;
- source-tag verification result;
- build procedure/toolchain classification when operationally required.

The manifest never records secrets, customer content, local absolute Delivery/Backup paths, or development database state.

## 13. Handoff Artifact Contract

Development hands off:

- installer;
- checksum file;
- release manifest;
- safe environment template;
- field installation/setup procedure;
- Philippine Seed Canary Runbook;
- Philippine Seed Execution Pack;
- Tenant Identity Constitution and approved identity sheet;
- Backup/Restore Runbook and packaged backup/verify instructions;
- release/field boundary evidence.

Development does not hand off populated tenant databases, real customer assets, Assignment Secret, development `.env`, development `dopamatrix.db`, development Delivery output, or development backup bundles.

## 14. V1.5 Scope

This boundary is limited to a local Windows V1.5 Seed release and the three approved Philippine tenant identities, beginning with `ph-elv-0001`. It does not authorize universal Default-ON, automatic ramp, cloud storage, live restore, multi-machine authority, a new project schema, or future L3 indexing.

## 15. Future AUTH-001 Boundary

AUTH-001 remains the future identity/membership/authorization architecture. V1.5 still requires a narrow field-safety control that prevents arbitrary or mistyped workspace labels from provisioning tenant databases.

That control may use an explicit local approved-tenant registry and operator provisioning command, but it must not collapse Canonical Tenant ID into user identity, Tenant Short Code, task identity, Reservation owner-attempt identity, or execution identity.
