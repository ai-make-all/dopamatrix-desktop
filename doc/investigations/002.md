提问：战友，你好！关于批次内多样性账本，我们打算优先去做，不过有个问题，要确认一下，我们现在的桌面端tauri用的本地数据库sqlite，多个并发任务去更新数据库，是否需要排队？批次内多样性账本的性能和稳定性如何保障

回答：战友，这个问题抓得非常准。结论先说：

> **需要“排队”，但不是让所有渲染任务排队。**
> **真正需要串行化的是“批次内多样性账本的占位/锁定动作”，也就是选素材那一瞬间。**
> **FFmpeg 渲染、AI 文案生成、代理生成、预览生成都可以并发跑。**

SQLite 本身适合你们 Tauri 胖客户端的本地架构，但要接受一个事实：

> **SQLite 可以多读并发，但同一时间只能有一个写事务。**

SQLite 官方 WAL 文档也明确说，WAL 模式下读写可以并发，但因为只有一个 WAL 文件，所以同一时间只能有一个 writer。([sqlite.org][1])
所以你们的设计重点不是“避免排队”，而是：

> **让需要排队的写操作极短、极少、原子化。**

---

# 一、先区分两类“usage_count”

你们这里千万不要只用一个 `usage_count` 字段解决所有问题。

至少要分成两层：

```text
1. global_usage_count
长期使用次数：这个素材历史上被多少成品使用过。

2. batch_reserved_count
批次内占用次数：本轮 batch 已经被多少 variant 预定使用。
```

如果只在渲染完成后更新 `usage_count`，就会出现你截图里说的问题：

```text
任务 1 选了 asset_A，但还没渲染完成
任务 2 / 3 / 4 不知道 asset_A 已经被选
于是它们也都选 asset_A
```

正确做法是：

> **素材一旦被某个 variant 选中，还没渲染，也要先写入 batch ledger，占一个“预定坑位”。**

---

# 二、推荐架构：先串行规划 Variant，再并发渲染

最稳的方案不是让 4 个渲染任务各自去抢素材，而是先做一个轻量的 **Variant Planning 阶段**。

```text
Matrix Batch 创建
↓
Variant Planner 生成 4 个 Variant Plan
↓
Batch Diversity Ledger 检查和占位
↓
确认 4 个 Variant Plan 不重复
↓
再把 4 个渲染任务丢进并发队列
```

也就是说：

```text
选素材 / 写账本：串行、短事务
渲染视频：并发、长任务
```

这就像买电影票：

```text
选座占座必须瞬间锁定
看电影可以大家同时看
```

对 DopaMatrix 来说：

> **不要让 FFmpeg worker 自己决定用哪个素材。**
> **应该由 Matrix Planner 先决定每个 variant 的素材组合，然后 worker 只负责按 Render Intent 渲染。**

---

# 三、SQLite 是否能扛住这个账本？

能扛住。因为 Batch Diversity Ledger 的写入非常轻。

一次 variant 占位大概只是写几行：

```text
variant_id
asset_id
asset_cluster_id
opening_signature
hook_text_hash
render_intent_hash
semantic_signature
```

这不是大文件写入，也不是高频日志流。即使 batch size 是 20、50、100，也完全适合 SQLite。

真正危险的是这几种错误做法：

```text
1. 在事务里跑 FFmpeg
2. 在事务里调用 AI 模型
3. 在事务里扫描大文件
4. 一个 worker 长时间占着数据库连接
5. 多个线程同时写 usage_count，没有唯一约束
6. 读写都共用一个长连接，导致锁等待
```

你们要保证：

> **数据库事务只做“检查 + 占位 + 提交”，不要做任何慢操作。**

---

# 四、SQLite 建议开启 WAL + busy_timeout

本地桌面端建议初始化数据库时执行：

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 5000;
PRAGMA foreign_keys = ON;
```

WAL 模式适合你们这种“UI 读很多、后台写一点、任务并发跑”的桌面端场景。SQLite 文档说明 WAL 提供 snapshot isolation，读事务会看到自己开始时的数据库快照；写入提交后，正在读的事务不会被中途打断。([sqlite.org][2])

但要注意：

> **WAL 不是多 writer。WAL 只是让读写并发更顺滑，不代表多个写事务可以同时写。**

所以还需要一个 **写入队列 / 事务锁 / planner 单写通道**。

# 五、最推荐的落地方案：单 Writer + 批次账本

## 方案结构

```text
Tauri UI
↓
Matrix Batch 创建
↓
Variant Planner
↓
Ledger Reservation Service
↓
SQLite 单写事务
↓
Render Queue 并发渲染
```

其中最关键的是：

```text
Ledger Reservation Service
```

它负责：

```text
检查是否重复
检查素材配额
检查 opening 3 秒是否重复
检查 asset_cluster 是否重复
检查 Hook 文案是否重复
写入 reservation
生成 Render Intent
```

渲染 worker 不直接改账本，只读取已经生成好的 Render Intent。

# 六、推荐数据表设计

## 1. 批次表

```sql
CREATE TABLE matrix_batches (
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL,
  recipe_id TEXT,
  batch_size INTEGER NOT NULL,
  status TEXT NOT NULL,
  diversity_policy_json TEXT,
  created_at TEXT NOT NULL
);
```

---

## 2. 变体表

```sql
CREATE TABLE matrix_variants (
  id TEXT PRIMARY KEY,
  batch_id TEXT NOT NULL,
  variant_index INTEGER NOT NULL,
  status TEXT NOT NULL,
  seed TEXT NOT NULL,

  render_intent_hash TEXT,
  timeline_signature TEXT,
  opening_signature TEXT,
  semantic_signature TEXT,

  render_intent_json TEXT,
  output_path TEXT,

  created_at TEXT NOT NULL,

  UNIQUE(batch_id, variant_index),
  UNIQUE(batch_id, render_intent_hash),
  UNIQUE(batch_id, opening_signature)
);
```

这里有两个关键唯一约束：

```sql
UNIQUE(batch_id, render_intent_hash)
UNIQUE(batch_id, opening_signature)
```

这样即使代码层漏了，数据库层也能拦住“完全一样的渲染计划”和“开头 3 秒重复”。

---

## 3. 素材占用表

```sql
CREATE TABLE batch_asset_reservations (
  id TEXT PRIMARY KEY,
  batch_id TEXT NOT NULL,
  variant_id TEXT NOT NULL,
  asset_id TEXT NOT NULL,
  asset_cluster_id TEXT,
  slot_type TEXT NOT NULL,
  beat_id TEXT,
  reservation_status TEXT NOT NULL,
  created_at TEXT NOT NULL,

  UNIQUE(batch_id, asset_id, slot_type),
  UNIQUE(batch_id, asset_cluster_id, slot_type)
);
```

如果你们当前最想避免 X 轴主素材重复，可以先只对 `x_primary` 生效。

例如：

```text
同一 batch 内，x_primary 的 asset_id 不允许重复。
同一 batch 内，x_primary 的 asset_cluster_id 不允许重复。
```

后续再放宽成：

```text
same_asset_cluster_max = 2
```

那就不要用简单唯一约束，而是用计数规则。

# 七、占位时必须用事务

每生成一个新 variant，做一次很短的事务。

推荐逻辑：

```sql
BEGIN IMMEDIATE;

-- 1. 检查 asset 是否已经被本 batch 占用
SELECT COUNT(*)
FROM batch_asset_reservations
WHERE batch_id = ?
  AND asset_id = ?
  AND slot_type = 'x_primary'
  AND reservation_status IN ('reserved', 'rendering', 'completed');

-- 2. 检查 asset_cluster 是否已经被占用
SELECT COUNT(*)
FROM batch_asset_reservations
WHERE batch_id = ?
  AND asset_cluster_id = ?
  AND slot_type = 'x_primary'
  AND reservation_status IN ('reserved', 'rendering', 'completed');

-- 3. 插入 variant
INSERT INTO matrix_variants (...);

-- 4. 插入素材占位
INSERT INTO batch_asset_reservations (...);

COMMIT;
```

`BEGIN IMMEDIATE` 的作用是尽早拿写锁，避免你先读一堆东西，最后写入时才发现被别人抢了。SQLite 官方事务文档说明，`BEGIN IMMEDIATE` 会立即启动写事务；如果另一个写事务已经活跃，它可能返回 `SQLITE_BUSY`。([sqlite.org][3])

所以业务层要做：

```text
如果 SQLITE_BUSY：
等待 / 重试 / 重新采样
```

# 八、还可以更稳：用 INSERT OR IGNORE 抢占

比“先查再插”更抗并发的方式，是直接依赖唯一约束抢占。

例如：

```sql
INSERT OR IGNORE INTO batch_asset_reservations (
  id,
  batch_id,
  variant_id,
  asset_id,
  asset_cluster_id,
  slot_type,
  beat_id,
  reservation_status,
  created_at
)
VALUES (?, ?, ?, ?, ?, 'x_primary', ?, 'reserved', datetime('now'));
```

然后检查受影响行数：

```text
row_count = 1：抢占成功
row_count = 0：说明已经有人占了，换素材
```

这比你在应用层自己判断更安全。

# 九、是否需要全局任务排队？

不需要全局排队。应该分三层：

## 1. Matrix Planner 队列：需要排队

这个队列负责“选素材 + 写账本”。

```text
一次只处理同一个 batch 的一个 variant reservation
```

或者：

```text
允许多个 batch 并行，但写 SQLite 时仍然走单 writer
```

## 2. Render Queue：可以并发

比如：

```text
VideoExecutor 并发 1–2
GraphicExecutor 并发 4–8
Metadata / 文案任务并发更多
```

视频渲染 CPU 重，不建议太多并发。

## 3. Attribution / 日志写入：可以异步批量写

投放表现、日志、进度，不要频繁单条同步写。可以：

```text
内存聚合
每 1–3 秒 flush 一次
或者任务状态变化时写一次
```

# 十、性能怎么保障？

关键是 6 条。

## 1. 账本事务要小

事务里只做：

```text
检查签名
插入 variant
插入 reservation
提交
```

不要做：

```text
素材扫描
AI 推理
视频渲染
大 JSON 生成
文件 hash 计算
```

---

## 2. 建索引

必须建这些索引：

```sql
CREATE INDEX idx_res_batch_asset
ON batch_asset_reservations(batch_id, asset_id, slot_type);

CREATE INDEX idx_res_batch_cluster
ON batch_asset_reservations(batch_id, asset_cluster_id, slot_type);

CREATE INDEX idx_variant_batch_opening
ON matrix_variants(batch_id, opening_signature);

CREATE INDEX idx_variant_batch_render_hash
ON matrix_variants(batch_id, render_intent_hash);

CREATE INDEX idx_variant_batch_semantic
ON matrix_variants(batch_id, semantic_signature);
```

---

## 3. 先生成候选池，再写账本

不要每个 variant 都重新全库搜索。

推荐：

```text
先根据 Growth Intent / Beat Requirement 生成候选池
↓
候选池保存在内存
↓
每个 variant 从候选池里采样
↓
只在占位时写 SQLite
```

这样 DB 压力非常小。

---

## 4. 使用内存账本 + SQLite 落库双层结构

同一个 batch 在单机内运行时，可以用：

```text
内存 ledger：快速检查
SQLite ledger：持久化和崩溃恢复
```

流程：

```text
内存先判断
↓
SQLite 事务最终确认
↓
成功后更新内存 ledger
```

SQLite 是最终事实来源。

---

## 5. 不要频繁更新 assets.usage_count

不要每选一次素材就直接：

```sql
UPDATE assets SET usage_count = usage_count + 1
```

这样会造成热点写。

更推荐：

```text
batch_asset_reservations 记录占用
↓
渲染完成后汇总
↓
批量更新 usage_count
```

或者把 usage_count 做成视图 / 统计表：

```sql
SELECT asset_id, COUNT(*)
FROM asset_usage_events
GROUP BY asset_id;
```

长期可以做事件表：

```text
asset_usage_events
- reserved
- rendered
- approved
- published
- failed
- released
```

这样更利于归因。

---

## 6. 异常任务要释放占位

如果 variant 渲染失败，要根据失败类型决定是否释放素材占位。

```text
素材不可用 / 文件失联：
释放占位，并标记素材异常

FFmpeg 临时失败：
可保留占位，重试

用户取消 batch：
释放所有 reserved / rendering 状态

渲染成功但审核驳回：
可以保留 usage 记录，但不计入 published usage
```

# 十一、稳定性怎么保障？

## 1. Reservation 状态机

不要只有 used / unused。

建议：

```text
reserved       已占位，尚未渲染
rendering      渲染中
rendered       已渲染
approved       审核通过
published      已发布
failed         渲染失败
released       已释放
cancelled      批次取消
```

这样系统崩溃后能恢复。

---

## 2. 启动时做恢复扫描

Tauri 桌面端可能会被用户直接关闭，所以启动项目时要检查：

```text
有没有 stuck reservations？
有没有 rendering 状态超过 2 小时？
有没有 variant 没有 output_path？
有没有 output 文件不存在？
```

然后提示：

```text
检测到上次未完成的 batch。
[继续渲染]
[释放占位]
[标记失败]
```

---

## 3. 每个 batch 有 run_id

不要只用 project_id。

```text
batch_id
run_id
variant_id
```

这样你们能追踪：

```text
这次生成为什么重复？
哪个策略导致候选不足？
哪个素材被哪个 variant 占了？
```

---

## 4. Ledger 写入要幂等

同一个 variant 重试时，不应该重复插入一堆占位。

可以用：

```text
variant_id 作为幂等键
```

如果再次提交同一个 variant_id：

```text
已有则返回当前状态
没有则创建
```

# 十二、推荐实现方式：不要让多个 worker 直接抢 DB

你们现在 Tauri + SQLite + 多任务，最稳结构是：

```text
MatrixPlannerService
  - 单线程 / 单 Actor
  - 负责生成 variant plan
  - 负责写 batch ledger

RenderWorkerPool
  - 多线程 / 多进程
  - 只消费已确认的 render_intent
  - 不参与素材选择

DbWriteQueue
  - 所有写操作统一排队
  - 小事务快速提交
```

如果你们后端是 Python FastAPI，本地 SQLite，可以这样：

```text
一个专门的 DB writer queue
多个 render worker
render worker 通过队列发状态更新
DB writer 统一写 SQLite
```

如果后端是 Rust/Tauri，也可以做成：

```text
tokio mpsc channel
↓
db_writer task
↓
SQLite connection
```

核心原则：

> **多 worker 可以并发计算，但不要多 worker 同时各自随意写账本。**

# 十三、最小可行版本怎么做？

你们现在优先解决 4 条生成完全一样的问题，MVP 可以这样做。

## MVP 规则

```text
1. 每个 batch 先串行生成所有 Variant Plan
2. 同一 batch 内 x_primary asset_id 不重复
3. 同一 batch 内 opening_signature 不重复
4. render_intent_hash 不重复
5. 生成完 Variant Plan 后再并发渲染
```

## MVP 流程

```text
create_batch(batch_size=4)
↓
for i in 1..4:
    generate candidate variant
    check in-memory ledger
    reserve in sqlite transaction
    if duplicate:
        retry up to 10 times
↓
if only got 2 valid variants:
    提示用户候选不足
↓
parallel_render(valid_variants)
```

这已经能解决 80% 的重复问题。

# 十四、候选不足时的产品提示也很重要

不要为了凑 batch_size 硬生成重复。

如果批量大小是 4，但系统只找到 2 个有效差异变体，要提示：

```text
当前计划生成 4 条，但根据去重规则只能生成 2 条有效差异变体。

原因：
- 可用 Hook 主素材只有 2 个
- near-win + failure_moment 素材不足
- opening 3 秒去重规则过严

建议：
[生成 2 条]
[放宽 asset_cluster 限制]
[允许同素材不同 Hook 文案]
[补充素材]
[切换到轻微变体模式]
```

这比生成 4 条一样的视频专业得多。

# 十五、最终建议

战友，你们这个 Batch Diversity Ledger 在 SQLite 上完全可以做，关键是不要把它设计成“多个渲染任务同时更新 usage_count”。

正确设计是：

```text
1. 先规划 variant
2. 用极短 SQLite 事务占位素材
3. 写入 batch ledger
4. 生成 render_intent_hash / opening_signature
5. 确认不重复
6. 再并发渲染
7. 渲染结果回写状态
8. 失败则释放或标记占位
```

一句话总结：

> **SQLite 里需要排队的是“素材占位和账本写入”，不是“视频渲染”。Batch Diversity Ledger 的性能瓶颈不在 SQLite，而在你们是否把选材占位做成了短事务、单写通道、可恢复状态机。**
