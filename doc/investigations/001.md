提问：战友，你好！这里有个matrix引擎多视频变体重复度的问题，我们现在1.0版本下，前面多轮测试发现有同时生成一模一样视频的情况（比如批量大小设置4,生成4个视频完全一模一样）！这里我想和战友探讨一下，目前成熟的matrix引擎，如何解决视频重复度的，有没有成熟的处理方案或者算法

回答：战友，这个问题是 **Matrix Engine 的核心质量问题**。批量设置 4，结果生成 4 个完全一样的视频，说明你们 1.0 现在还只是“批量渲染”，还没有真正进入“矩阵变体规划”。

一句话判断：

> **成熟 Matrix 引擎不是先随机生成 4 次，而是先规划 4 个必须不同的 Variant Plan，再进入素材寻址和渲染。**
> **重复度控制必须发生在渲染前、渲染中、渲染后三个阶段。**

# 一、为什么 1.0 会生成完全一样的视频？

常见原因一般有 8 个。

## 1. 随机种子相同

比如 4 个任务同时启动，都使用同一个随机种子，或者用秒级时间戳做 seed，导致抽样结果一致。

```text
variant_01 seed = 123
variant_02 seed = 123
variant_03 seed = 123
variant_04 seed = 123
```

结果自然一样。

---

## 2. 候选素材池太小

比如 Hook Beat 需要：

```text
near-win + boss_low_hp + failure_moment + TikTok Ready
```

过滤后只剩 1 个素材，那么生成 4 个视频都会选它。

---

## 3. 打分模型每次都取 Top 1

如果 Asset Matcher 每次都选最高分素材，而且没有 batch 内 diversity penalty，就会一直选同一个。

```text
asset_A score = 0.92
asset_B score = 0.81
asset_C score = 0.76
```

如果每次都取 `asset_A`，那批量生成就会重复。

---

## 4. usage_count 没有在批次内实时更新

很多系统只在渲染完成后才更新素材使用次数。
但 4 个任务是并发启动的，任务 2、3、4 并不知道任务 1 已经选了 asset_A。

正确做法是要有：

```text
Batch Diversity Ledger / 批次内多样性账本
```

也就是在本轮 batch 内先锁定已选素材，避免重复。

---

## 5. locked 模式锁死了素材

如果 DSL 里写了 `asset_hashes`，并且每个 Beat 都是 locked 模式，那么 Matrix Engine 再怎么批量，都会渲染同一个结构。

这不是 Bug，而是策略冲突：

```text
用户说要矩阵
但 DSL 说素材强锁定
```

这种情况下系统应该提示：

```text
当前为强锁定素材模式，无法生成有效变体。是否改为 Soft Lock 或 Similar Pool？
```

---

## 6. fallback 兜底素材重复

如果找不到合适素材，系统每次都回落到同一个 B-roll、安全空镜、默认贴纸、默认 CTA，也会造成重复。

---

## 7. Render Intent 完全一样

如果 4 个视频的 Render Intent JSON 完全相同，渲染出来必然相同。

所以渲染前必须计算：

```text
render_intent_hash
timeline_signature
asset_sequence_hash
```

只要这些 hash 完全一样，就不应该进入渲染。

---

## 8. 缓存 key 设计错误

有些系统为了加速，会缓存渲染结果。
如果缓存 key 没有包含 variant_id、seed、素材组合、文案组合，可能 4 个任务都命中同一个缓存结果。

---

# 二、成熟 Matrix Engine 的核心方案：先做 Variant Plan，再渲染

成熟方案不是：

```text
生成视频 1
生成视频 2
生成视频 3
生成视频 4
```

而是：

```text
先生成 4 个 Variant Plan
↓
检查 4 个计划是否足够不同
↓
再进入素材寻址
↓
再生成 Semantic Timeline
↓
再渲染视频
↓
渲染后再次去重
```

也就是：

```text
Matrix Intent
↓
Variant Planner
↓
Diversity Constraint
↓
Asset Matcher
↓
Timeline Compiler
↓
Pre-render Dedup
↓
Render
↓
Post-render Dedup
```

你们现在的问题，很可能就是少了 **Variant Planner + Diversity Gate**。

---

# 三、什么叫 Variant Plan？

一个变体不能只靠“随机”。
它应该是一个明确的计划对象。

例如：

```yaml
variant_plan:
  variant_id: v_001
  batch_id: batch_2026_001

  variation_axes:
    hook_type: near_win_failure
    opening_asset_cluster: boss_low_hp_cluster_A
    emotion_arc: frustration_to_retry
    cta_type: playable_try_now
    caption_style: challenge_question
    bgm_style: tension_fast
    sticker_style: shock_alert
    subtitle_style: bold_yellow
    language: Taglish
    platform: TikTok

  uniqueness_requirements:
    min_axis_diff_from_others: 3
    opening_3s_must_be_unique: true
    main_asset_sequence_must_be_unique: true
    hook_text_must_be_unique: true
```

重点是：

> **每个变体在进入渲染前，就必须知道自己和其他变体有什么不同。**

# 四、成熟系统一般控制哪些“重复度维度”？

视频重复不是一个层面的问题，而是多层重复。

## 1. 文件级重复

两个视频文件完全一样。

检测方式：

```text
file_hash
```

这个最简单。

---

## 2. Render Intent 重复

两个视频还没渲染，但渲染指令完全一样。

检测方式：

```text
render_intent_hash
```

例如：

```text
同一个模板
同一组素材
同一个时间线
同一套字幕
同一个 CTA
同一个 BGM
```

这种必须在渲染前拦截。

---

## 3. Timeline 重复

文件可能不同，但时间线结构一样。

检测方式：

```text
timeline_signature
```

例如：

```text
Hook Beat 用 asset_A
Conflict Beat 用 asset_B
CTA Beat 用 asset_C
每个 Beat 时长都一样
Y 轴贴纸也一样
```

这也应该拦截。

---

## 4. 视觉感知重复

文件 hash 不同，但用户看起来几乎一样。

比如只是码率不同、字幕轻微变化、导出文件不同。

检测方式：

```text
perceptual hash / pHash
关键帧相似度
CLIP embedding 相似度
```

---

## 5. 语义重复

视觉不完全一样，但投放意义一样。

例如 4 条都是：

```text
Boss 残血失败 + 同一句 Hook + 同一个 CTA
```

即使换了贴纸，也算“买量测试价值很低”。

检测方式：

```text
semantic_signature
```

例如：

```text
story_node + emotion_arc + hook_type + cta_type + asset_cluster
```

---

# 五、成熟 Matrix Engine 的三道去重门

## 第一道：生成前去重

在生成 Variant Plan 时就做约束。

例如：

```text
本批次 4 个视频：
- Hook 文案不能重复
- 开头 3 秒主素材不能重复
- 主视频素材序列不能完全重复
- 同一素材 cluster 最多出现 1 次
- CTA 可以重复，但视觉结构不能完全重复
```

这是最重要的一道。

---

## 第二道：渲染前去重

每个 Render Intent 生成后，计算：

```text
render_intent_hash
timeline_signature
asset_sequence_hash
semantic_signature
```

如果和本批次已有视频重复：

```text
不渲染
重新采样
或者提示素材不足
```

这一步能避免浪费 FFmpeg 渲染时间。

---

## 第三道：渲染后去重

渲染完成后，做最终检测：

```text
file_hash
关键帧 pHash
首 3 秒相似度
整体视觉相似度
音频指纹
字幕文本相似度
```

如果重复：

```text
标记 duplicate
不进入 Review Queue
触发自动再生成
或者进入“重复风险”队列
```

---

# 六、成熟算法方案

## 方案 1：Batch Diversity Ledger 批次多样性账本

这是最应该先做的 MVP 方案。

每次生成 batch 时维护一个账本：

```yaml
batch_diversity_ledger:
  used_assets:
    - asset_A
    - asset_B

  used_asset_clusters:
    - boss_fail_cluster_01

  used_hook_texts:
    - "Can you beat this boss?"

  used_story_nodes:
    near_win: 2
    guild_rescue: 1

  used_cta_types:
    playable_try: 2
    download_now: 1

  used_render_hashes:
    - xxx
    - yyy
```

每生成一个新变体，都检查：

```text
是否和已有变体重复？
是否超过素材使用配额？
是否开头 3 秒重复？
是否 Hook 文案重复？
是否 asset cluster 重复？
```

这个方案最实用，优先级最高。

---

## 方案 2：Quota Constraint 配额约束

不要让系统无限使用同一个轴。

例如：

```yaml
diversity_policy:
  batch_size: 4

  constraints:
    same_opening_asset_max: 1
    same_main_asset_sequence_max: 1
    same_asset_cluster_max: 1
    same_hook_text_max: 1
    same_cta_text_max: 2
    same_bgm_max: 2
    same_template_max: 2
    same_story_node_max: 2
```

这比纯随机稳定得多。

例如生成 4 条时：

```text
Variant 1：near-win + Boss素材A + Hook文案A + CTA A
Variant 2：near-win + Boss素材B + Hook文案B + CTA B
Variant 3：guild rescue + 公会素材A + Hook文案C + CTA A
Variant 4：character awakening + 觉醒素材A + Hook文案D + CTA B
```

这样至少不会完全一样。

---

## 方案 3：Variation Axis 变体轴控制

成熟 Matrix 不是所有东西都随机，而是指定本轮要变化哪些轴。

常见变体轴：

```text
Story Node
Emotion Arc
Hook 类型
开头 3 秒主素材
字幕文案
CTA
BGM
贴纸
评论卡
封面
语言
平台规格
时长
节奏
结尾 End Card
Playable 入口
```

你们可以在 Matrix Lab 里让投手选择：

```text
本轮主要测试什么？

[测试 Hook]
[测试 Story Node]
[测试 CTA]
[测试语言]
[测试 Playable 入口]
[测试素材组合]
[测试封面 / 标题]
```

如果投手选“测试 Hook”，系统就应该保证 Hook 不重复。
如果选“测试 CTA”，系统就可以保持前面结构一致，只改变 CTA。

这叫：

> **Controlled Variation / 受控变体。**

它比“随机变体”更适合买量测试。

---

## 方案 4：Max-Min Diversity 最大最小距离

这个适合从候选池里选 N 个差异最大的组合。

思路：

```text
先生成 50 个候选 Variant Plan
↓
计算它们两两之间的差异度
↓
从中挑 4 个彼此最不相似的
```

差异度可以这样算：

```text
variant_distance =
  Hook 差异
+ Story Node 差异
+ 素材 cluster 差异
+ CTA 差异
+ BGM 差异
+ 字幕差异
+ 视觉 embedding 差异
```

这个方案比直接随机抽 4 个更稳。

---

## 方案 5：MMR 多样性重排序

MMR 是推荐系统里常用的思路。
它不是只选最高分，而是在“质量”和“差异性”之间平衡。

普通选择：

```text
永远选最高分素材
```

MMR 选择：

```text
既要高分，也要和已经选过的不一样
```

例如：

```text
asset_A 分数最高，但已经和 Variant 1 很像
asset_B 分数略低，但差异更大
```

那么 Variant 2 应该选 asset_B。

这对 Asset Compass 很有用。

---

## 方案 6：Cluster-level 去重

只禁止同一个文件重复还不够，因为同一段素材可能有多个版本：

```text
boss_fail_v1.mp4
boss_fail_crop.mp4
boss_fail_with_subtitle.mp4
boss_fail_export2.mp4
```

文件 hash 不同，但内容一样。

所以要引入：

```text
asset_cluster_id
```

同一类近似素材归为一个 cluster。

规则：

```text
同一 batch 内，同一个 asset_cluster_id 最多使用 1 次或 2 次。
```

Cluster 可以来自：

```text
pHash 相似
CLIP embedding 相似
同源文件
人工合并
同一时间码切片
```

---

## 方案 7：Opening 3 Seconds Uniqueness

买量视频最重要的是前 3 秒。
即使后面不同，如果前 3 秒一样，平台和用户都会认为高度重复。

所以建议单独做：

```text
opening_signature
```

包含：

```text
开头主素材
开头字幕
开头 Hook
开头音效
开头视觉布局
```

规则：

```text
同一 batch 内 opening_signature 不允许重复。
```

这比全片去重更重要。

# 七、DopaMatrix 应该怎么改 1.0？

我建议你们分三阶段。

---

## Phase 1：立刻修复完全重复问题

这是最低成本版本。

### 必做 1：每个 variant 独立 seed

```python
seed = hash(batch_id + variant_index + recipe_id)
```

不要让 4 个任务共享同一个 seed。

---

### 必做 2：生成前建立 batch ledger

```python
ledger = BatchDiversityLedger()

for i in range(batch_size):
    candidate = generate_variant(seed=i)

    while ledger.is_duplicate(candidate):
        candidate = regenerate_variant()

    ledger.add(candidate)
    render(candidate)
```

---

### 必做 3：Render Intent hash 去重

进入 FFmpeg 前，计算：

```text
render_intent_hash
```

如果已经存在：

```text
跳过，重新生成
```

---

### 必做 4：同批次主素材不重复

最少要加：

```text
same_x_primary_asset_max = 1
same_opening_asset_max = 1
```

否则 matrix 没意义。

---

### 必做 5：候选不足时不要硬生成重复

如果 batch_size = 4，但符合条件的素材只有 1 个，系统应该提示：

```text
当前候选素材不足，最多只能生成 1 条有效差异变体。
是否放宽条件？
[放宽标签]
[允许同素材不同文案]
[允许同素材不同 CTA]
[补充素材]
```

不要静默生成 4 条一样的。

---

## Phase 2：建立真正的 Variant Planner

引入：

```text
Matrix Plan
Variant Plan
Diversity Policy
Variation Axis
```

数据结构：

```yaml
matrix_plan:
  batch_size: 4
  test_goal: test_hook_and_cta

  variation_axes:
    - hook_text
    - opening_asset
    - cta
    - subtitle_style

  fixed_axes:
    - story_node
    - emotion_arc
    - platform
    - language

  diversity_policy:
    same_opening_asset_max: 1
    same_hook_text_max: 1
    same_cta_text_max: 2
    min_axis_diff: 3
```

这样投手能明确知道：

```text
这一批到底在测试什么变量。
```

---

## Phase 3：做感知去重和情绪结构去重

进一步加：

```text
pHash
CLIP embedding
audio fingerprint
subtitle similarity
semantic_signature
```

例如：

```text
semantic_signature =
story_node + emotion_arc + hook_type + cta_type + asset_cluster_sequence
```

如果语义结构完全一致，即使文件不一样，也要提示：

```text
该变体与 Variant 2 在投放语义上高度相似，建议替换 Hook 或 Story Node。
```

# 八、UI 上怎么体现重复度控制？

Matrix Lab 里应该有一个 **重复度控制面板**。

## 1. 变体强度

```text
变体强度：

[轻微变体]
只改标题 / CTA / 字幕 / 贴纸

[中等变体]
改 Hook / 开头素材 / 评论卡 / BGM

[强变体]
改 Story Node / Emotion Arc / 主素材组合 / Playable 入口
```

---

## 2. 不重复规则

```text
本批次去重规则：

[✓] 开头 3 秒不重复
[✓] Hook 文案不重复
[✓] 主素材序列不重复
[✓] 同一素材簇最多使用 1 次
[ ] CTA 可重复
[ ] BGM 可重复
```

---

## 3. 候选素材不足提示

```text
当前设置计划生成 20 条，但有效候选组合只有 12 条。

原因：
- near-win + failure_moment 素材只有 3 个
- 可用于 Hook 的 Taglish 文案只有 4 条
- 公会召唤素材缺少真实玩法证明

建议：
[生成 12 条]
[放宽素材标签]
[允许同素材不同文案]
[补充素材]
```

这个体验会比静默重复专业很多。

# 九、重复度不是越低越好，要看测试目的

这里有个高级点：买量矩阵不是一定要所有东西都不同。

如果你在测试 CTA，就应该固定其他变量，只改 CTA。
如果你在测试 Hook，就应该固定后半段，只改开头。
如果你在测试 Story Node，就应该让 Story Node 不同，其他尽量一致。

所以成熟 Matrix Engine 的原则是：

> **不是追求随机差异，而是追求受控差异。**

例如：

## 测试 Hook

```text
固定：
Story Node、CTA、BGM、后半段素材

变化：
开头 3 秒、Hook 文案、开头字幕
```

## 测试 CTA

```text
固定：
Hook、主素材、情绪曲线

变化：
CTA 文案、按钮、End Card、Playable 入口
```

## 测试情绪路径

```text
固定：
市场、平台、语言

变化：
near-win / 公会召唤 / 角色觉醒
```

所以你们 UI 里应该让投手先选：

```text
本轮测试目标是什么？
```

然后系统自动生成对应的 diversity policy。

# 十一、最终判断

战友，成熟 Matrix Engine 解决重复度，不是靠“多随机几次”，而是靠一套完整机制：

```text
变体规划
↓
变体轴控制
↓
批次多样性账本
↓
素材配额约束
↓
语义签名
↓
渲染前 hash 去重
↓
渲染后感知去重
↓
候选不足提示
```

一句话总结：

> **Matrix 引擎不是批量渲染器，而是受控实验设计器。它必须先保证每个变体在增长测试意义上不同，再去调素材、编时间线和渲染。**
