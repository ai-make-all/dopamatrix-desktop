# 1、这种“只发相关文件 review 后迭代”的方式是否可行？

可行，但要满足 4 个条件。

第一，文件不能只发最终渲染文件。要覆盖“从 batch_size 到 render_intent”的完整链路。
第二，每次只让 AI 做一个明确目标，不要同时改 Matrix、DB、UI、渲染、素材匹配。
第三，每次执行后必须产出报告，包括改了哪些文件、为什么改、怎么测、还有哪些风险。
第四，所有新能力都要先“旁路接入”，不要一上来重构 1.0 主链路。

你第一批最好给我或给 Cursor 审的文件范围是这些：

```text
1. 批量生成入口文件
   负责读取 batch_size、循环创建任务、调用渲染。

2. DSL / Recipe 解析文件
   例如 dsl_parser.py、director_blueprint.jinja、recipe builder 相关文件。

3. 素材寻址 / Asset Resolver 文件
   负责 smart / locked 模式、semantic_tags、asset_hashes、usage_count、fallback。

4. Render Intent / Timeline 生成文件
   负责把 beat、素材、字幕、贴纸、音效编译成渲染参数。

5. 渲染任务队列文件
   负责并发、状态、FFmpeg 调用、输出路径。

6. SQLite 访问层 / schema / migration 文件
   负责资产表、任务表、使用次数、状态写入。

7. 当前 Matrix UI 或 API 入口
   负责从前端传 batch_size、模板、生成参数到后端。
```

如果你只能先发 3–5 个文件，那优先级是：

```text
批量生成入口 > 素材寻址 > Render Intent 生成 > SQLite 访问层 > 渲染队列
```

# 6、最终判断

战友，你这个协作方式是可行的，而且很适合你们目前的小团队状态。

真正要避免的是：

```text
把一堆代码丢给 AI，然后说“帮我升级到 1.5”
```

正确方式是：

```text
先让 AI 建代码地图
再让 AI 找问题链路
再让 AI 做最小设计
再分步骤改
每步跑测试
每步回传报告
再由我继续校准方向
```

一句话总结：

> **这次 1.0 → 1.5，不要做成一次大手术，要做成 10 个可回滚的小补丁。你把关键文件和 Cursor 执行报告持续反馈给我，我就能逐轮把迭代指令压得越来越准。**
